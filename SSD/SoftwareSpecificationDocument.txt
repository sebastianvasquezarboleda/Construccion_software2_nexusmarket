SOFTWARE SPECIFICATION DOCUMENT (SSD)
NEXUSMARKET

1. PURPOSE

NexusMarket is a marketplace application organized into domain, application,
and adapter layers. The application provides REST endpoints and stores domain
data in MongoDB.

2. DOMAIN MODELS

User
- Attributes: id, fullName, normalized email, normalized documentNumber, role,
  status, and a BCrypt password hash stored with the user record.
- Behaviors: activate, block, query whether the user is active, and change
  password. Password hashes are never returned by the API.

Buyer
- Attributes: id, userId, mainAddress, additionalAddresses, commercialStatus.
- Behaviors: add and remove additional addresses.

Seller
- Attributes: id, userId.

Warehouse
- Attributes: id, name, type, and optional sellerId for seller-owned warehouses.

Product
- Attributes: id, sellerId, name, description, type, price, variants, status.
- Behaviors: publish, suspend, discontinue, add variants, identify physical
  or digital product.

Inventory
- Attributes: id, productId, warehouseId, sellable quantity, damagedQuantity,
  movements.
- Behaviors: add, reserve, remove, return, adjust stock, and query available
  quantity.
- Each movement records its type, absolute quantity, resulting stock, and
  timestamp. Movements are stored with their inventory document in MongoDB.
- A new inventory with positive opening quantity creates an ENTRY movement;
  quantity zero starts without a movement.
- Add, reserve, remove, return, and adjust operations record ENTRY,
  RESERVATION, SALE_OUT, RETURN, and ADJUSTMENT movements respectively.
- Damaged stock is excluded from sellable quantity and recorded as DAMAGED.
- Confirming payment records an idempotent SALE_OUT movement linked to the order;
  quantity was already deducted during reservation.
- Inventory documents use optimistic version checks to prevent concurrent
  updates from overselling a stock bin.
- A physical order item records exact inventory-bin allocations. Reservations
  span bins by ascending inventory ID and return to those same bins.

Order
- Attributes: id, buyerId, items (including inventory allocations), status,
  total, createdAt, updatedAt, and optimistic version.
- Behaviors: add and remove products, update total, send to payment, mark as
  paid, dispatch, finalize, and cancel.
- Cancellation moves the order to the terminal CANCELLED status.

Invoice
- Attributes: id, orderId, buyerId, line items, total, issue timestamp.
- One internal invoice is created idempotently when an order is marked paid.

Shipment
- Attributes: id, orderId, deliveryAddress, status.
- Internal status flow: CREATED -> PACKED -> DISPATCHED -> DELIVERED.

ReturnRequest
- Attributes: id, orderId, buyerId, productId, quantity, reason, status,
  creation timestamp, and inventory allocations.
- Status flow: REQUESTED -> APPROVED or REJECTED; an approved request can be
  recorded as REFUNDED.

AdministrativeSummary
- Aggregated order counts by state, gross sales, sellable inventory, and
  damaged inventory.

3. ENUMERATIONS

Role: BUYER, SELLER, LOGISTICS_OPERATOR, ADMINISTRATOR, SUPERVISOR.
UserStatus: ACTIVE, BLOCKED.
WarehouseType: MARKETPLACE, SELLER.
ProductType: PHYSICAL, DIGITAL.
ProductStatus: PUBLISHED, SUSPENDED, DISCONTINUED.
InventoryMovementType: ENTRY, RESERVATION, SALE_OUT, ADJUSTMENT, RETURN,
DAMAGED.
OrderStatus: CART, PENDING_PAYMENT, PAID, DISPATCHED, FINALIZED, CANCELLED.
ShipmentStatus: CREATED, PACKED, DISPATCHED, DELIVERED.
ReturnStatus: REQUESTED, APPROVED, REJECTED, REFUNDED.

4. DOMAIN RULES

- Required fields must be provided; enum fields use defined enum values.
- Inventory quantity cannot be negative, and a reservation cannot exceed
  available stock across all bins for a product.
- Positive quantities are required for stock add, reserve, remove, and return.
- An empty order cannot be sent to payment.
- Order status transitions are validated by the domain model.
- A finalized order cannot be cancelled or modified.
- A cancelled order cannot be reused or cancelled again.
- Only CART and PENDING_PAYMENT orders can be cancelled. A paid or dispatched
  order cannot be cancelled and return stock to available inventory.
- CART and PENDING_PAYMENT orders expire after 30 minutes without activity;
  their reserved physical inventory is returned automatically. The expiration
  scan runs once per minute.
- A buyer does not submit the product price. The order snapshots the current
  catalog price and accepts only products in PUBLISHED status.
- Order stock changes validate the order operation before changing inventory;
  failed persistence operations attempt to compensate stock changes.
- Digital products do not reserve physical inventory and orders containing only
  digital products are finalized when marked paid; digital file delivery is
  not part of this implementation.
- Email and identity document values are unique after normalization.
- Passwords have a minimum length of 12 characters and are stored as BCrypt
  hashes on the user record.
- Buyers can access only their own buyer/order data; sellers can manage their
  products and associated inventory. Other operations are role-restricted.
- Invoices are internal records without tax calculation or external billing
  integrations. Refund status is manual and does not transfer money.
- Returns can only be requested for finalized physical orders and cannot exceed
  the unreturned purchased quantity; the remaining quantity is reserved
  atomically per order and product. Rejected requests release that reservation.
  Approval is persisted with a conditional status transition, and its inventory
  restoration is idempotent so retries cannot return the same units twice.
- A discontinued product cannot be published again.
- Buyer addresses are required, trimmed, and deduplicated.

5. APPLICATION AND HEXAGONAL ARCHITECTURE

- application/domain/models/: domain entities and value models.
- application/domain/enums/: domain enumerations.
- application/domain/ports/in/: input ports used by the REST adapter.
- application/domain/ports/out/: persistence ports.
- application/services/: application services implementing the input ports.
- application/api/: REST controllers and HTTP exception handling.
- application/adapters/out/persistence/entity/: MongoDB persistence classes.
- application/adapters/out/persistence/repository/: Spring Data MongoDB
  repository interfaces.
- application/adapters/out/persistence/: MongoDB adapters implementing the
  output ports.
- application/adapters/out/memory/: in-memory adapters used in tests.
- src/test/java/: domain, application service, adapter, and MongoDB integration
  tests.

The REST controller depends on input-port interfaces, not on concrete service
classes. Services implement these input ports and depend on output-port
interfaces. MongoDB adapters implement the output ports.

6. REST API

Base URL: http://localhost:8080/api

Authentication: HTTP Basic is required for every API route.
State-changing requests require CSRF protection. GET /csrf returns the token
and header name; clients send the token in X-XSRF-TOKEN and the XSRF-TOKEN
cookie on POST, PUT, PATCH, and DELETE requests.

CSRF bootstrap:
- GET /csrf

Users:
- GET /users, GET /users/{id}, POST /users.
- PATCH /users/{id}/activate, PATCH /users/{id}/block.
- PUT /users/{id}/password (administrator only).

Buyers:
- GET /buyers, GET /buyers/{id}, POST /buyers.
- POST /buyers/{id}/addresses, DELETE /buyers/{id}/addresses?address={value}.

Sellers:
- GET /sellers, GET /sellers/{id}, POST /sellers.

Warehouses:
- GET /warehouses, GET /warehouses/{id}, POST /warehouses.

Products:
- GET /products, GET /products/{id}, POST /products.
- PATCH /products/{id}/price with a JSON price.
- PATCH /products/{id}/publish, PATCH /products/{id}/suspend,
  PATCH /products/{id}/discontinue.
- POST /products/{id}/variants.

Inventory:
- GET /inventories, GET /inventories/{id}, POST /inventories.
- PATCH /inventories/{id}/add?amount={value}.
- PATCH /inventories/{id}/reserve?amount={value}.
- PATCH /inventories/{id}/remove?amount={value}.
- PATCH /inventories/{id}/return?amount={value}.
- PATCH /inventories/{id}/adjust?quantity={value}.
- PATCH /inventories/{id}/damage?amount={value}.

Orders:
- GET /orders, GET /orders/{id}, POST /orders.
- POST /orders/{id}/products.
- DELETE /orders/{id}/products/{productId}.
- PATCH /orders/{id}/payment, /paid, /dispatch, /finalize, and /cancel.
- GET /orders/{id}/invoice.

Invoices:
- GET /invoices, GET /invoices/{id}.

Shipments:
- POST /shipments, GET /shipments, GET /shipments/{id},
  GET /orders/{id}/shipment.
- PATCH /shipments/{id}/pack, /dispatch, and /deliver.

Returns:
- POST /returns, GET /returns, GET /returns/{id}.
- PATCH /returns/{id}/approve, /reject, and /refund.

Reports:
- GET /reports/summary.

Domain and malformed-request validation errors are returned as HTTP 400
responses. Unexpected server errors are logged and returned with a generic
message. Successful creation requests return HTTP 201; other successful
requests return HTTP 200.

7. MONGODB AND AUTHENTICATION

The main application uses MONGODB_URI. By default it connects to
mongodb://localhost:27017/nexusmarket. MongoDB persistence classes are mapped
to collections for buyers, inventories, orders, products, sellers, users, warehouses, invoices, shipments, and returns.
Password hashes are stored on user documents. Inventory movements
and order inventory allocations are embedded in their parent documents.
Inventory documents include a version used for optimistic concurrency control.
User IDs are numeric Long values in the current model. Existing user documents
with string IDs require migration before listing those records through the API.
Existing product documents need a price assigned before they can be added to
orders. Existing duplicate buyer/seller user associations must be reconciled
before the new unique indexes are created.

Set NEXUSMARKET_ADMIN_EMAIL and NEXUSMARKET_ADMIN_PASSWORD before startup to
create or reactivate the initial administrator. Both values are required
together; if neither is set, no initial administrator is created. Passwords
must contain at least 12 characters. New users can be registered by an
administrator through POST /api/users; the request includes a password.

For isolated demonstrations, activate the demo profile. It uses
MONGODB_DEMO_URI or defaults to mongodb://localhost:27017/nexusmarket_demo.
This profile does not modify or delete data in the default nexusmarket database:

.\mvnw.cmd spring-boot:run "-Dspring-boot.run.profiles=demo"

The opt-in MongoDB integration test uses MONGODB_TEST_URI and defaults to the
nexusmarket_test database. Run it from nexusmarket/nexusmarket with:

.\mvnw.cmd '-Dmongodb.integration=true' '-Dtest=MongoPersistenceIntegrationTest' test

Cart expiration defaults to 30 minutes and a 60-second scan interval. Configure
NEXUSMARKET_CART_EXPIRATION with an ISO-8601 duration and
NEXUSMARKET_CART_EXPIRATION_SCAN_MS with the scan interval in milliseconds.

For deployments, terminate TLS at a trusted reverse proxy, restrict direct
access to the Spring Boot port, and overwrite forwarded headers at the proxy.
Configure exact frontend origins with NEXUSMARKET_CORS_ALLOWED_ORIGINS.
CSRF cookies are Secure by default; local HTTP demo mode disables Secure.
Configure NEXUSMARKET_CSRF_COOKIE_SAME_SITE=None only for cross-site HTTPS
frontends that require it.

8. ALIGNMENT AND IMPLEMENTATION LIMITS

The API implements HTTP Basic authentication, CSRF protection, role checks and resource ownership,
normalized identity uniqueness, seller/product/warehouse association, damaged
stock, multi-bin physical reservations, order lifecycle, internal invoices,
internal shipment lifecycle, returns with stock restoration, manual refund
status, and an administrative summary.

The following integrations or capabilities are outside the current scope:
- External payment gateway, fiscal/tax invoice calculation, and carrier
  integration.
- Actual money transfer during a refund.
- Digital file hosting, access control, or download delivery.
- Warehouse selection based on distance, cost, capacity, or delivery route.
  The current deterministic policy consumes stock by ascending inventory ID.
- A migration utility for older user records whose IDs were stored as strings.


9. POSTMAN

The Postman collection is located at:
nexusmarket/nexusmarket/postman/NexusMarket.postman_collection.json

Import it into Postman, set baseUrl to http://localhost:8080, and provide
adminEmail and adminPassword locally in Postman. The shared collection leaves
both credential values blank; configure the same credentials as
NEXUSMARKET_ADMIN_EMAIL and NEXUSMARKET_ADMIN_PASSWORD before startup. Run the
61 requests in their listed order; they cover users, role ownership, inventory,
orders, invoices, shipments, returns, and reports.

10. VERIFICATION

Run all unit and adapter tests:

.\mvnw.cmd test

Run MongoDB persistence integration tests separately using the command in
section 7 when MongoDB is available.
